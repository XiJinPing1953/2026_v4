# 账务当前决定

## 2026-09-12期间抹零展示

用户要求实际收款卡片新增抹零汇总，适用于所有客户。`period_summary`新增`.3`契约，抹零单列，不计实际收款或净收款；对账与两导出使用同一后端结果，保留既有明细和余额计算。

源单自身抹零按源单业务日期，正式收款抹零按收款业务日期，分配及目标快照只去重核验。旧单无正式背书的内嵌抹零按既有源单日期口径披露，并明确缺少独立抹零日期；此约定不用于推导现金到账。期初预付款及后续预付/待分配收款再分配的抹零，按有效分配单登记的业务日期归集，并明确这可能沿用原收款日、不代表实际操作日；缺少该业务日期时待核。取数不完整、缺日期、背书冲突不显示确定的抹零合计；独立抹零待核不影响已核实现金合计。

代码及验证见[本轮交接](../handoffs/2026-09-12-rounding-and-deposit.md)，部署状态以STATE为准。押金资金能力已获用户批准并进入独立实施；生产状态以STATE为准，存瓶不等于押金资金记录。

适用：销售金额、客户结算、管理汇总及导出。当前目标与实际交付状态见 [STATE](../../STATE.md)，凭证入口见 [ACCOUNTING](../../docs/ACCOUNTING.md)。

## A-01：结算归属明确后才计算（2026-09-05）

来源：用户批准的“数据可信与反复返工”改造计划；历史业务迁移见旧 STATE `2026-03-27 客户对账页承接 m3 计费`。本决定替代“看到 m3 就把所有旧销售归零”以及“缺少模式就当普通销售”的两种推断。

- 新建 m³ 客户销售默认 `settlement_mode=customer_flow`：销售只记录重量/流转，流量结算单形成应收。
- 已存单据明确为 `customer_flow` 时，销售应收为零；明确为 `sale` 时按该单计费，包括明确归属的历史 m³ 销售。
- 旧 m³ 单据缺失或无效模式时，详情仍可读取并显示金额为待核（null），账务合计、导出和涉及账务的变更返回 `FINANCIAL_CLASSIFICATION_REQUIRED`（409）及待核源单，不能选择 0 或气量乘价作为确定值。
- 逐笔核查客户、期间、流量结算与来源关联；只因同客户、同期间或金额相近不能认定覆盖。没有可靠对应证据的单据保持待核，不自动修账。
- 权威后端模块为 [saleAccounting.js](../../uniCloud-alipay/cloudfunctions/common/saleAccounting.js)；销售/结算及导出使用相同规则及版本，部署副本由统一同步工具管理。代码合入、测试、线上状态分开记录。

## A-02：营收、应收和现金不能互相代替（2026-05-15，2026-09-05确认）

来源：旧 STATE `2026-05-15 累计营收保留历史销售抹零前金额`、`累计营收/实收排除期初历史欠款`，以及本轮批准计划；替代早期把期初、抹零和净应收混入本期营收的汇总口径。

- 营收使用明确归属的销售/流量及本期其他费用来源；期初历史欠款参与余额但不算本期营收。2026-09-08 按用户确认修订收款展示：偿还历史欠款的实际到账计入收款日期对应期间的实际收款，详见 A-06；旧 amount_received_total 字段保留兼容，不再直接作为页面“实际收款”。
- 有效应收表达扣除抹零等后的债权；现金收款、非现金冲抵、退款、未分配预收和期初余额分别展示、可追溯到来源。
- 退款保留负号；冲抵和抹零不冒充现金。销售自身实收与客户收款分配不能重复计入。
- 整车优先使用出厂毛重减回厂毛重和已明确的结算称重；代理销售按关联代理灌装，不伪装成普通瓶销售。
- 修改统计或导出时保留来源类型、来源 ID、业务日期、规则版本和计算完整性。累计与期间指标使用相同字段定义，不能只比较总金额。

## A-06：营收与实际收款分开汇总（2026-09-08）

来源：用户确认本年营收不受历史回款影响、跨年查询应收包含历史款项的显示方案，并明确授权实施。替代 A-02 中把偿还历史欠款的收款排除出“实际收款”展示的旧口径；历史欠款的来源分类与已结清状态不变。

- period_summary 是对账页与两种单客户导出的统一新增契约；旧汇总字段保留，客户列表/首页不随此次补丁更改口径。
- 适用于所有客户，按请求客户 ID 和各自数据计算，没有指定客户白名单或固定金额。A-05 的专用修账只针对已确认客户，不能与本条通用汇总规则混淆。规则通用不代表所有客户历史数据已逐户核清；缺少依据仍显示待核。

- 单户与批量日表共用展示函数，保留两位/三位金额精度；缺版本、缺字段或读取未完成显示待核，不能补零。
- 导出修复验收与客户整户核准分开：余额一致不证明期初、收款日期和凭证已经补齐。

## A-11：有会计日期的旧内嵌已收转正式收款（2026-09-11）

来源：K001逐户核账中，用户确认会计记-024为2026-02-07收款11,500元，并明确授权转换。补充A-06/A-10中“缺日期保持待核”的处理：只有取得客户、金额、到账日期和目标销售的明确依据后，才能退出历史日期推导。

- 转换只补充1张正式收款和逐单分配，不增加销售`amount_received`，不迁移销售抹零或非现金冲抵；已有正式背书先扣除，避免现金与冲抵重复。
- 收款方式缺证时保存`unknown`。确认实际收到款不等于确认现金、银行、微信等具体渠道。
- 专用入口固定客户、金额、日期、目标源单及确定编号；执行前完整双读、保存原值和计划，事务中故意中断与完整写后回滚均通过后才能提交。重复执行返回原批次，不再新增收款。
- 原始销售只允许推进`updated_at`建立并发保护，业务字段不变。提交后完整回读必须只出现计划内的1张收款、9条分配及10行元数据时间变化。

- 这是K001的证据化转换流程，不表示其他客户的旧内嵌已收可以按销售日期自动转换；其他客户仍逐户取得外部凭据并生成独立锁定计划。

## A-12：冲抵额度可按真实退款拆分（2026-09-12，已发布后端）

来源：K002保定灰鲸酒店逐户核账。用户确认1260元退液中270元用于抵扣瓶租、990元于2026-02-02实际退付；补充A-02/A-06对负销售、非现金冲抵和现金退款的区分。

- 负销售形成的冲抵额度可部分分配给应收目标，其余未分配额度只有取得真实退款日期和金额后才能转成正式现金退款。已分配冲抵不计现金；正式退款计入`refund_total`并减少`net_cash_received`。
- 转换仅允许超级管理员执行，必须先只读预览，并提供固定`operation_id`、确认文本和冲抵源单的金额、分配、未分配、既退金额及版本原值。事务内再次核对；重试返回同一结果。
- 始终满足“冲抵总额＝已分配＋抹零分配＋未分配＋已转现金退款”。超额、作废来源、原值变化或不完整余额均拒绝写入。
- 该能力不处理押金。押金收退继续与销售营收、客户气款及期间现金汇总分开。

实现：`crm-customer-settlement/offsetCreditRefund.js`及受限动作`previewOffsetCreditCashRefundV1`、`convertOffsetCreditToCashRefundV1`；反例见`scripts/offsetCreditCashRefund.test.cjs`。源码`ded5e46`已上传客户结算完整函数，线上预览动作回读通过；尚未用于K002写账。
