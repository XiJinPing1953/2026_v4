# 工程约束与协作契约

本文件保存长期工程约束。业务语义以 [领域索引](../state/INDEX.md) 中当前决定为准；执行状态以 [STATE](../STATE.md) 为准。用户在当前任务明确的新决定覆盖过时的本地指导，须记录替代关系。代码是实现证据，不能把实现缺陷升格成业务规则。

## 归属与兼容

- 保留 uni-app Vue 3 + Vite、uniCloud 支付宝云及现有硬件路线；不随意移动 `uniCloud-alipay/` 或更改 `src/manifest.json` 的平台绑定。
- `src/pages/**` 只做路由、布局和编排；组件负责交互，composables 负责交互状态，后端负责权限、权威业务计算和写入。
- 前端历史适配集中在 `src/services/mappers/**`；后端历史适配集中在所属领域的数据入口模块。不得把后端兼容塞入前端，也不得在多个组件复制金额或流转规则。
- 多个云函数共用的业务规则维护单一源码，独立部署副本必须由同步工具产生并检查一致性。不要只拆文件而保留多套计算。
- 前端通过 `src/services/api/**` 调云函数；认证由 `src/services/auth.js`、导航由 `src/services/navigation.js` 处理。
- HBuilderX 实际上传入口是 `uniCloud-alipay/database/` 根目录。根目录与 `database/schema/` 同名时，以根目录为唯一编辑来源并由同步脚本生成旧目录副本；只存在于旧目录的 schema 暂按历史文件保留。改动这类集合时，须先核对线上结构，再把 schema 与 `.index.json` 提升到根目录，不能直接覆盖未知的线上约束。

## 数据可信与外部写入

- 对账、库存、异常判断依赖完整取数；展示分页不能作为完整业务计算输入。不完整或历史归属不明时，返回可识别的未完成/待核状态，不用 0 或“无异常”冒充确定结论。
- 保留源单事实及变更证据。历史修正与规则归一、结构拆分分别交付，不根据新的默认值批量改写旧账。
- 同一操作重试须能查询已保存结果，关联处理可恢复且幂等；历史改单后的旧任务不得覆盖新版本结果。
- 云数据操作先确认 provider、space-id、范围，完成预览、备份或可恢复方案，再在已有授权范围内执行并核对。增量导入使用确定键匹配的 update/upsert；禁止把 `--initdatabase` 用作常规导入/清理。
- 本地原始导出、凭证、token、客户明细不进入上下文索引或发布清单。索引只保存必要的脱敏元数据、计数、哈希和报告位置。

## 任务执行与验证

- 实现或修复任务按风险明确目标、涉及范围和完成条件，检查相关差异及前置修复；简单解释、只读查询和文案修改直接处理，不套完整工程流程。常规实现选择由代理承担；需要改变账务归属、删除范围或现场控制行为而现有证据不足时，才向用户提出具体未决点。
- 完成已授权目标及必要验证后结束；无关问题只记录，不自动扩展改造。未完成时说明具体阻塞与继续条件，不用笼统“是否继续”代替推进。
- 等待必须有具体对象、继续条件和失败出口；不把某次发布等待时长固化为固定流程。可选偏好采用合理默认值，必要业务事实缺失时明确提问；失败操作按可恢复协议处理，不反复查询终止状态。
- 修复近期回归先对照最新变更与最小失败路径。结论必须区分“用户决定”“本地代码事实”“测试证据”“历史报告”“本轮线上验收”。
- 验证按风险选择：账务和状态写入用真实业务入口及事故反例；普通展示修改做相关平台构建和视觉核查。通过后不因流程惯性反复扩测。同一源码、产物和环境的有效结果可复用；仅相关改动、失败、新证据或环境变化触发重跑，并说明原因。线上验收验证部署及实际行为，不重复全部本地测试。
- PDA 原生插件/AAR 变更要重打自定义基座或安装包并在真机安装验证；H5 构建不能证明原生修复。Windows 网关现场设备、断线与联锁验收单列。
- 并行工作仅用于边界清晰且已获授权的子任务；避免多人同时修改核心账务，同一负责人合并证据与交付结论。
- 用户已授权按需拆解子任务；只在有独立交付且有并行收益时派发，每个代理负责一个明确结果。主任务审查关键证据与分歧，不重做全部明细；简单解释和单处文档修改通常直接完成。
- 模型偏好（2026-09-13用户更新，替代09-08的Astra极高安排）：凡选择GPT-6，使用GPT-6 Astra轻度（low）；GPT-5.6 Sol保持Ultra。派发时显式设置对应档位；历史任务的模型记录仅为当时事实，不用于新任务。当前任务的模型/推理设置由应用控制，文档不能证明已切换。
- 独立工作区先核对前置修复，修改范围互斥，主任务统一合并和发布；新任务使用已更新main，未发布灌装/PDA/导入任务使用对应开发分支及候选基线。
- 发布须对应源码提交、产物哈希、目标环境及依赖云函数/schema。网页、PDA 和各网关分别版本化；未核实的运行版本写“未核实”。发布成功不等于关键业务验收通过。
- 发布检查以当前 `config/release-products.json` 中明确的函数、数据库变更及运行文件清单为范围，不将某次四函数发布固化为长期范围。开发分支保持全仓检查，显式`--scope=all`能力不变。若实际生产保留历史公共副本，须以Git中的规范源码完整提交和SHA-256绑定并强制检查所需文件，不以关闭检查或漏掉缺失文件保留兼容；是否改变该行为另行审查。

## 上下文维护

- STATE 只维护当前任务、运行版本、阻塞与证据入口，保持不超过150行，不用长段落挤进行数上限；客户控制数和发布过程留在对应记录。历史原文存入 `state/history/` 并记录 SHA-256、字节数和行数，不再作为默认指令加载。
- 业务规则仅在相应领域文件维护，记录适用范围、来源日期、替代关系、代码/测试证据。README、CLAUDE、个人技能只引用入口。
- 客户核准结果以逐户核账记录为准，当前发布状态以STATE为准，系统总表只维护里程碑和链接；旧记录标明日期及后续替代，避免多处维护同一状态。
- [交接模板](../state/handoffs/TEMPLATE.md) 仅在有跨任务保留价值的变更时记录已做、证据、未做、下一步和发布状态；普通问答无需更新STATE或创建交接，领域文件只在业务决定改变时更新；不要把计划写成完成事实。
- [可靠性证据与指标](SYSTEM_RELIABILITY.md) 跟踪返工、待核账差、未完成同步、版本不匹配；无测量数据写“未测量”，不能推算成零。
- 文档改动运行 `node scripts/checkProjectContext.cjs`；检查仅遍历显式当前入口和领域文件，不把归档文本当现行指令。

## 分支与合并

- main收敛已验收内容；生产版本以发布回执及运行版本为准，合并或推送不代表已部署。
- 历史发布提交在对应交接中定位；开发分支的灌装/PDA/导入及schema须完成独立验收后再按范围合并，不整支带入。
- 采用正常前进合并，保留已上线权限差异与源码依据；本地无关文件和原始账务证据不随合并提交。
