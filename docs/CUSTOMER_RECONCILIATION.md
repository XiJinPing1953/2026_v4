# 通用客户对账工作流

2026-10-13 用户批准将已有整批核查和受保护修正接成独立“对账中心”。核查计算、导入和修复按问题类型复用，客户及依据作为处理数据；不再为同类客户问题新建云函数。原 CLI 只读工作流继续保留。实现、测试及实际发布分别见[本次交接](../state/handoffs/2026-10-13-reconciliation-center.md)和[STATE](../STATE.md)，本文不代表已经上线。

## 对账中心

入口为 `/pages/accounting/reconciliation-center`。财务、管理员、超级管理员沿用页面权限；原收款日期及同笔收款依据修正仍仅限超级管理员。客户对账页负责单户阅读，对账中心负责整批来源、差异和复核。

1. 导入好会计整张“应收统计表”，填写与报表一致的账套名称和确认的入账截止日。只支持同年 01-01 至截止日；报表月份必须一致，文件本身的月份不能证明具体入账日。原始文件、字节哈希及截止日随批次保存，相同文件/账套/截止日复用原批次，同一操作号不能换输入。
2. 确认 CRM 结算客户与好会计科目的对应关系并填写依据。映射按账套复用，一主户可以对应多个科目，同一科目不能交给不同客户；同名只列候选。客户范围包含隐藏、停用和别名，隐藏或合并来源尚不能可靠自动核验时保持待核，不能以界面看不到为由省略。
3. 开始或继续逐户核查，按客户、核查状态或问题类型筛选。请求失败保留待核，可暂停后继续；先检查 CRM 原单、分配及可用余额，再比较双方期初、发生、收回和期末。重复核查更新本批同户结果并保留变化审计，不新增重复待办。
4. 导入差异科目的“明细账”。每份必须同账套、同期间、覆盖到确认截止日，并与统计表的科目编码、名称和四项控制数一致。原文件缺编码时才允许指定编码补齐；原编码与指定编码冲突不能覆盖。多科目客户须提供完整科目范围才能确认逐笔结果。按日期和借贷比较；同额异日、拆并记录及额外同额记录只是候选，不自动改账或删除。
5. 在单户详情选择有依据的处理：抹零冲回、多收款结清，或超级管理员使用日期/收款依据修正。先预览，确认后用固定操作号提交并复核；同一户可以逐项处理。仅原始账务已完整通过而六项客户汇总缓存过期时允许自动刷新；收款可用金额、销售已收和其他原单字段不属于缓存。
6. “好会计待处理”只登记依据，不关闭差异；会计补记后重新导入，再核查。人工核准绑定当前来源和结果，不能跳过已知差异或证据不足。中心不写好会计、不自动生成凭证，也不替用户修改旧核账清单。

单文件限原始 `.xls/.xlsx`、2 MiB；唯一识别有效报表，校验表头、逐行平衡及合计。公式、错误单元格、超限工作表、缺行或损坏文件拒绝；不把公式缺缓存当作零。原始证据可在中心下载，不进入 Git、发布清单或普通上下文索引。

## 核对程度与恢复

- **汇总一致**只表示四项控制数一致；没有明细时仍为明细待核。逐笔金额错误相互抵消也可能汇总一致。**明细一致**表示日期和借贷逐笔对应，不证明现金、退款或非现金调整性质；备注不能代替凭证。**人工核准**另记确认人、依据、证据层级和来源版本。
- 取数完整性、反向关系和双读哈希用于发现可检测的变化，仍不是跨集合原子快照。核查是带时间的观察；重新打开批次先标待复核，重新取源后才恢复当前结论。原单、映射或文件变化后原核准失效；截止日后的业务不宣称已与好会计一致。当前版本没有无人值守巡检和自动取数。
- 修正超时先查询原操作号；已提交但写后未核实的操作继续回读，不重记一笔。通用收款修正以实际写后快照等于受保护计划哈希确认本次操作完成；同户其他问题仍单列待核。已验证操作的历史证据保持，后续新业务只影响当前整户核查。操作协议详见[受保护修正](ACCOUNTING_CORRECTION.md)。

## 只读 CLI 每次运行

以下本地工具读取报表及 CRM 接口并生成独立 Excel，不写客户账务、客户缓存或核账清单。K 系列专用函数保留历史记录，不作为日常核查入口。CLI 和中心共用 `common/customerReconciliation.js` 的纯计算，旧模块路径保留兼容。

1. 先由使用者确认好会计已入账的**具体截止日**。在好会计登录页选对账套和该日所在月份，从“应收统计表”导出整张报表，不用网页首屏可见的少数行代替文件。原文件保存在本机受控目录。
2. 准备经确认的 `mapping.json`：`{"schema_version":1,"mappings":[{"crm_customer_id":"...","accountant_codes":["..."],"basis":"确认依据"}]}`。一个 CRM 结算主户可对应多个好会计科目；同名仅列候选，不能自动写入映射。别名客户归入其 CRM 结算主户，但在报告“CRM客户范围”中逐户列出。
3. 使用有权读取全部客户（包括停用、隐藏）的超级管理员会话运行。示例：

   ```sh
   node scripts/runCustomerReconciliation.cjs \
     --accounting=/受控目录/应收统计表.xls \
     --date-from=2026-01-01 --cutoff=2026-09-23 \
     --mapping=/受控目录/mapping.json \
     --token-file=/受控目录/session.local \
     --space-id=实际云空间ID \
     --out=outputs/trust-audit/customer-reconciliation-YYYYMMDD
   ```

   当前版本只支持同一公历年从 1 月 1 日至确认截止日。输出目录必须是受控且不会进入 Git 的位置；旧批次不覆盖。程序校验好会计账套、月份、科目编码唯一性、逐行月度平衡、整表合计、CRM 全量分页与再次读取的一致性。任何缺页、重复、期间不一致或读取不完整都不能给出全体对平结论。

4. 先看 Excel“来源与口径”，再按“客户对账”状态筛选。“会计科目”保留整张好会计科目范围，“CRM客户范围”列出所有 CRM 客户与结算主户关系，“异常与待办”列差异和待确认映射。只有明确映射且四个控制数相等、CRM 取数完整的客户，才列为“数字对平·待人工核准”。
5. 对已映射的异常户才导出该户好会计“明细账”，期间须与整批相同。写入如下清单，再运行逐笔定位：

   ```json
   {"crm_customer_id":"客户ID","accounting_files":[{"code":"好会计科目编码","path":"/受控目录/该科目明细.xlsx"}]}
   ```

   ```sh
   node scripts/analyzeCustomerReconciliationDetails.cjs \
     --run=outputs/trust-audit/customer-reconciliation-YYYYMMDD \
     --manifest=/受控目录/detail-manifest.json \
     --out=/受控目录/detail-comparison.json
   ```

   逐笔程序先核对科目名、期间及四个控制数与本批汇总完全一致，再按日期、借方、贷方精确配对。同额异日只列定位候选；摘要和接口投影不证明到账、退款或冲抵性质。需要修账时仍须取得原始依据并走受保护流程。

6. 审核员确认后，才另行更新既有核账清单，并记录本次截止日。截止日之后的新业务留到下一批。
