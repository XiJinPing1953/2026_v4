# 通用客户对账工作流

本工具只读好会计导出和 CRM 对账接口，生成独立 Excel。它不改客户总览、不写账务，也不修改核账清单。数字对平只表示同期间的账簿控制数相等，状态仍为“待人工核准”。K 系列专用函数保留作历史修账工具，不作为日常核查入口。

## 每次运行

1. 先由使用者确认好会计已入账的**具体截止日**。在好会计登录页选对账套和该日所在月份，从“应收统计表”导出整张报表，不用网页首屏可见的少数行代替文件。原文件保存在本机受控目录。
2. 准备经确认的 `mapping.json`：`{"schema_version":1,"mappings":[{"crm_customer_id":"...","accountant_codes":["..."],"basis":"确认依据"}]}`。一个 CRM 结算主户可对应多个好会计科目；同名仅列候选，不能自动写入映射。别名客户归入其 CRM 结算主户，但在报告“CRM客户范围”中逐户列出。
3. 使用有权读取全部客户（包括停用、隐藏）的超级管理员会话运行。示例：

   ```sh
   node scripts/runCustomerReconciliation.cjs \
     --accounting=/受控目录/应收统计表.xls \
     --date-from=2026-01-01 --cutoff=2026-09-23 \
     --mapping=/受控目录/mapping.json \
     --token-file=/受控目录/session.local \
     --space-id=实际云空间ID \
     --out=outputs/trust-audit/customer-reconciliation-YYYYMMDD
   ```

   当前版本只支持同一公历年从 1 月 1 日至确认截止日。输出目录必须是受控且不会进入 Git 的位置；旧批次不覆盖。程序校验好会计账套、月份、科目编码唯一性、逐行月度平衡、整表合计、CRM 全量分页与再次读取的一致性。任何缺页、重复、期间不一致或读取不完整都不能给出全体对平结论。

4. 先看 Excel“来源与口径”，再按“客户对账”状态筛选。“会计科目”保留整张好会计科目范围，“CRM客户范围”列出所有 CRM 客户与结算主户关系，“异常与待办”列差异和待确认映射。只有明确映射且四个控制数相等、CRM 取数完整的客户，才列为“数字对平·待人工核准”。
5. 对已映射的异常户才导出该户好会计“明细账”，期间须与整批相同。写入如下清单，再运行逐笔定位：

   ```json
   {"crm_customer_id":"客户ID","accounting_files":[{"code":"好会计科目编码","path":"/受控目录/该科目明细.xlsx"}]}
   ```

   ```sh
   node scripts/analyzeCustomerReconciliationDetails.cjs \
     --run=outputs/trust-audit/customer-reconciliation-YYYYMMDD \
     --manifest=/受控目录/detail-manifest.json \
     --out=/受控目录/detail-comparison.json
   ```

   逐笔程序先核对科目名、期间及四个控制数与本批汇总完全一致，再按日期、借方、贷方精确配对。同额异日只列定位候选；摘要和接口投影不证明到账、退款或冲抵性质。需要修账时仍须取得原始依据并走受保护流程。

6. 审核员确认后，才另行更新既有核账清单，并记录本次截止日。截止日之后的新业务留到下一批。
