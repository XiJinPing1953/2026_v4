# 受保护收款修正工具

2026-09-13用户单独批准实施。适用于有明确会计依据、独立结算且金额为两位小数的客户；首批为K006。只补齐同笔旧收款依据或调整已确认日期，不提供任意字段修改、重建全账、新增现金、退款、期初或押金迁移。

## 两类操作

- `complete_receipt_backing`：保留原正式收款编号，将已在普通销售记过、但缺正式分配的金额补入同一笔收款。补齐后分配须精确等于销售原已收；不增加销售已收。原收款须按指定目标分配且没有未分配余额。可将明确属于该笔收款的销售抹零转为收款抹零：销售原价、总抹零及欠款不变，日期随正式收款；原值保留在审计备份中。
- `correct_receipt_date`：保留收款金额和分配目标，只调整收款日期及沿用该日期的分配业务日期。遇到独立的后续分配日期时拒绝自动调整。分配不能早于目标业务日期。原收款渠道、凭据和备注保持。

其他来源、合并结算、跨客户关系、未完成调整、精度或取数不足均停止。通用能力通过不等于任何客户自动获得修账授权；每户仍须先确认金额、日期和对应关系。

## 执行及证据

函数为`crm-accounting-correction`，仅超级管理员可用；入口为`inspectV1 / prepareV1 / statusV1 / rehearseV1 / executeV1`。操作工具见`scripts/runAccountingCorrection.cjs`，请求只接受两类业务操作，不接收任意数据库补丁。原始数据及请求保存于受控本地目录，不进入Git。

1. 完整备份客户、销售、收款、分配、期初、流量、押金及相关凭证等原值；反向检查关联范围，记录读取时间和哈希。缺失可选集合单列，不用查询错误冒充空集合。
2. 用固定`operation_id`、预期原值哈希、用户依据哈希和源码提交生成预览；服务器编译逐项变化并保存审计记录。同批不同请求拒绝复用。
3. 事务再次检查原值、批次锁及确定编号，回滚演练后才允许正式提交；提交前复查范围。超时先查同批状态，不重新生成批次。
4. 写后完整回读，与预览预期哈希及逐字段差异比较，再核对三个账务入口、日期边界及页面。业务合计和原值证据各自验证。

原值读取和提交前范围复查不是跨集合原子快照，也不代表已解决全系统写入并发问题；未通过原值或范围检查时禁止继续。首次能力发布使用本地失败、冲突、权限、客户隔离及幂等测试，并做本批云端回滚。后续相同工具的有效测试按RULES复用，保留每批原值与写后核验；当前执行入口仍要求本批完整云端回滚。

账务规则和运行版本分别见[账务领域](../state/domains/accounting.md)和[STATE](../STATE.md)。此工具独立发布，无H5或数据库结构变更；已有其他客户专用修正记录保持历史版本。

## 人工核准待办（2026-09-13，独立于修账）

用户在K007明确要求保留原账务并收起已确认事项。`approveManualReviewV1`仅允许超级管理员登记一条核准审计：绑定客户、原值哈希、固定操作号、确认依据校验值、逐项金额、会计日期和凭证号。既有销售、收款、分配及余额不写入，不产生正式收款凭据。

对账和两种导出保留原现金完整性及空金额，新增`manual_review`说明人工处理状态；前端将已确认事项从待办中移出，相关空合计显示“已人工核准”，不改成0或伪造正式收款合计。未确认的新问题仍提示。核准与整个客户财务来源指纹绑定，源单、收款或分配变化后旧核准不再适用。核准记录不可当现金单据使用。运行版本、批次和验收见STATE及K007交接。
