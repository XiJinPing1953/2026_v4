# 受保护收款修正工具

2026-09-13用户单独批准实施，2026-10-14增加已确认多收款的旧费用重分类。适用于有明确业务依据、独立结算且金额为两位小数的客户；首批为K006。不提供任意字段修改、重建全账、新增现金、退款、期初或押金迁移。

2026-10-14用户明确长期边界：任何情况下不代用户操作好会计。CRM按真实业务及确认依据修正，好会计资料仅作核对参考；发现其错误向用户提醒，提醒会计核对处理，不能为凑平两边数字改写CRM事实。

## 三类操作

- `complete_receipt_backing`：保留原正式收款编号，将已在普通销售记过、但缺正式分配的金额补入同一笔收款。补齐后分配须精确等于销售原已收；不增加销售已收。原收款须按指定目标分配且没有未分配余额。可将明确属于该笔收款的销售抹零转为收款抹零：销售原价、总抹零及欠款不变，日期随正式收款；原值保留在审计备份中。
- `correct_receipt_date`：保留收款金额和分配目标，只调整收款日期及沿用该日期的分配业务日期。遇到独立的后续分配日期时拒绝自动调整。分配不能早于目标业务日期。原收款渠道、凭据和备注保持。
- `reclassify_overpayment_settlement`：将一笔已明确双方同意不退款、不抵以后货款、却记为其他费用的多付款，重分类为`prepay_writeoff`。原费用及其现金/优惠分配作废留痕；将原费用上的优惠移到指定销售，等额减少该销售的现金分配，再以释放的余额建立结清及分配。保留原到账金额、日期、渠道及收款优惠总额，销售原价、客户欠款和预付余额不变；结清单列收益，不新增现金或气款营收。

第三类当前每批仅一笔：须指定原收款、旧费用、承接优惠的销售、结清日期及两项金额，且`0 < 优惠 < 结清金额 < 原到账金额`。原款须已全额分配、可用余额为0；旧费用金额等于结清金额，恰由本笔现金及优惠独占结清。全部原分配限普通正额销售及指定费用，销售现金和优惠须与全部有效来源守恒；有出纳到账主记录时还须验证金额、日期、渠道及关联。退款、有效CRM凭证、相关结清/冲回占用或不明来源均拒绝。旧费用与销售日期不得晚于到账，结清不得早于到账。

未完成调整原则上停止。第三类仅允许在请求明确给出原调整编号、原款仍为`pending`、`deferred`、快照为`null`且保留开始时间，并通过上述原分配守恒检查时，随同一修正事务收尾；保存原编号、快照缺失事实和本次操作号，不是通用清除状态入口。其他待调整记录、合并结算、跨客户关系、精度或取数不足仍停止。通用能力通过不等于任何客户自动获得修账授权；每户仍须先确认金额、日期和对应关系。

## 执行及证据

函数为`crm-accounting-correction`，仅超级管理员可用；入口为`inspectV1 / prepareV1 / statusV1 / rehearseV1 / executeV1`。操作工具见`scripts/runAccountingCorrection.cjs`，通用请求接受上述三类业务操作，不接收任意数据库补丁。历史专用修正保留原限定范围，不作为新的通用类型。原始数据及请求保存于受控本地目录，不进入Git。

1. 完整备份客户、销售、收款、出纳到账主记录、分配、期初、流量、押金及相关凭证等原值；反向检查关联范围，记录读取时间和哈希。缺失可选集合单列，不用查询错误冒充空集合。
2. 用固定`operation_id`、预期原值哈希、用户依据哈希和源码依据生成预览；服务器编译逐项变化并保存审计记录。同批不同请求拒绝复用。源码依据接受40位`source_commit`或64位`source_sha256`，不替代用户依据`approval_sha256`和原值哈希。
3. 事务再次检查原值、批次锁及确定编号，回滚演练后才允许正式提交；提交前复查范围。超时先查同批状态，不重新生成批次。
4. 写后完整回读，与预览预期哈希及逐字段差异比较，再核对三个账务入口、日期边界及页面。业务合计和原值证据各自验证。

第三类编译器为`overpaymentSettlementRepair.js`，源码`aa9b60c`、计划版本`accounting-correction/2026-10-14.1`，复用固定编号、完整原值、事务演练、幂等及写后哈希协议。该源码记录不表示已完成云端发布、历史账务执行或现场验收；实际状态另见STATE及本批交接。

原值读取和提交前范围复查不是跨集合原子快照，也不代表已解决全系统写入并发问题；未通过原值或范围检查时禁止继续。首次能力发布使用本地失败、冲突、权限、客户隔离及幂等测试，并做本批云端回滚。后续相同工具的有效测试按RULES复用，保留每批原值与写后核验；当前执行入口仍要求本批完整云端回滚。

账务规则和运行版本分别见[账务领域](../state/domains/accounting.md)和[STATE](../STATE.md)。2026-09-13首版为独立后端发布，无H5或数据库结构变更；已有其他客户专用修正记录保持历史版本。

## 对账中心调用协议（2026-10-13）

`crm-reconciliation` 通过 `repairSourcesV1 / prepareRepairV1 / executeRepairV1 / repairStatusV1` 仅编排`complete_receipt_backing`和`correct_receipt_date`两类修正，保留超级管理员限制，不新增任意数据库修改入口。第三类当前仅由上述受保护CLI/API执行，尚未接入中心页面或修复编排。来源查询不等于修账授权，用户仍须选择原收款、填写日期或逐单金额及依据、查看实际变化再确认。

- 中心预览先重核结果版本，再取得保护工具的完整原值；传入固定操作号、原值哈希、确认依据哈希。`source_sha256`绑定编排实现源码及规则版本，原保护工具的计划版本、事务原值校验和回滚演练继续生效。
- 编排记录和底层修正共用同一客户及操作号；超时或关闭页面后查询原号。明确拒绝的预览可更正后重新生成方案；状态未知时先查原操作，不另开一笔。已提交操作只续做验证，不重复执行；并发占用、范围变化和跨客户来源仍拒绝。
- `verification.scope=repair_operation`、`verification.complete=true`只表示本次实际写后快照与底层保存的`after_snapshot_hash`一致。`customer_complete`、双方汇总/明细结果另外记录；一户还有别的问题不妨碍已完成的本笔修正结束，也不代表整户已核清。
- 提交后尚未验证就发生新变更时，保留`committed`，记录预期/实测快照差异并待核；不能冒充写后验证通过。已完成验证的历史记录不被后续新业务重写，重新核查结果独立保存。

本地事务替身已验证恢复协议；实际生产写入、云端回滚及历史客户核准另记，不能以本地通过代替。实现及交付边界见[对账中心交接](../state/handoffs/2026-10-13-reconciliation-center.md)。

## 人工核准待办（2026-09-13，独立于修账）

用户在K007明确要求保留原账务并收起已确认事项。`approveManualReviewV1`仅允许超级管理员登记一条核准审计：绑定客户、原值哈希、固定操作号、确认依据校验值、逐项金额、会计日期和凭证号。既有销售、收款、分配及余额不写入，不产生正式收款凭据。

对账和两种导出保留原现金完整性及空金额，新增`manual_review`说明人工处理状态；前端将已确认事项从待办中移出，相关空合计显示“已人工核准”，不改成0或伪造正式收款合计。未确认的新问题仍提示。核准与整个客户财务来源指纹绑定，源单、收款或分配变化后旧核准不再适用。核准记录不可当现金单据使用。运行版本、批次和验收见STATE及K007交接。
